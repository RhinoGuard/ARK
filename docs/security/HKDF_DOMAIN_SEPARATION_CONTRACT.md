# ARK HKDF-SHA-256 Contract and Purpose Registry

- Scope: CCB-01/06 and CCB-02 under Issue #29.
- Status: Crypto-owner decision proposal; independent security review and explicit owner confirmation are still required.
- Implementation: `crates/ark-crypto/src/kdf/hkdf_sha256.rs`.

## 1. Scope

`ark-crypto` implements HKDF-SHA-256 using the maintained RustCrypto `hkdf` and `sha2` crates. The production API derives fixed 32-byte, zeroizing subkeys under a closed ARK v1 purpose registry. It does not implement root-key generation, authorization, storage, AEAD, or key-wrapper lifecycle.

## 2. IKM trust and provenance contract (CCB-01/06)

### 2.1 What validation proves

`HkdfIkm::from_slice` rejects empty IKM and values shorter than `MIN_IKM_LEN = 16` bytes. `HkdfIkm::from_key_array` accepts a fixed 32-byte array.

These checks prove only that the input has an allowed representation/length. They do **not** prove entropy, unpredictability, origin, freshness, secrecy, or that the value is a cryptographic key. A 16-byte all-zero value passes the length wrapper; a regression test explicitly records this limitation so future readers do not infer a provenance guarantee.

### 2.2 Accepted production sources

The caller must supply high-entropy key material from an approved upstream source, currently limited to these intended categories:

1. A 32-byte KEK derived by the reviewed ARK Argon2id API from a password and a valid salt, when that KEK is the intended parent material for the selected purpose.
2. A 32-byte random root key generated by an approved OS CSPRNG through the future credential/key-lifecycle owner.

The following are not accepted production IKM sources: raw human passwords, usernames, account IDs, device IDs, timestamps, process IDs, ordinary identifiers, low-entropy tokens, arbitrary file contents, or byte strings selected only because they meet the 16-byte minimum.

### 2.3 Caller obligations and current API limitation

The caller is responsible for establishing source provenance before constructing `HkdfIkm`. The current KDF-only crate receives a byte slice and cannot authenticate its origin. No API or test in this crate claims otherwise.

The future key-lifecycle/broker boundary must own approved root-key generation and distribution, and must ensure the caller cannot substitute an arbitrary low-entropy byte string. That service does not yet exist in the current workspace. Do not interpret this wrapper as an attestation or capability.

The minimum-length check remains useful as a defensive truncation/degenerate-input guard. It is not an entropy estimator.

## 3. Registered HKDF purposes (CCB-02)

The following six labels are the current ARK v1 registry proposal. Each label has a distinct intended cryptographic domain. The enum derives a fixed context label; it does not itself implement the operation named by the purpose.

| Enum variant | Canonical context bytes | Intended output ownership / use |
|---|---|---|
| `WorkspaceKey` | `ARK/v1/workspace-key` | Workspace credential/key-wrapper subsystem; key material dedicated to wrapping or protecting the workspace root key. |
| `ProjectKey` | `ARK/v1/project-key` | Workspace/project key hierarchy; project-scoped key derivation, not a direct authorization grant. |
| `FileKey` | `ARK/v1/file-key` | Future storage/crypto integration; file payload key material, subject to a separately reviewed AEAD and nonce design. |
| `MetadataKey` | `ARK/v1/metadata-key` | Future storage-format owner; authenticated protection of security-critical metadata, not a substitute for specifying canonical serialization or AEAD. |
| `AuditKey` | `ARK/v1/audit-key` | Future audit subsystem; dedicated audit-integrity key material, not proof of tamper-evident logging until that subsystem exists. |
| `RecoveryKey` | `ARK/v1/recovery-key` | Future recovery/package owner; recovery-wrapper key material, not a recovery ceremony or escrow implementation. |

### 3.1 Decision proposal and compatibility rules

The proposed Crypto-owner decision is to retain all six existing enum variants and exact byte labels as the canonical ARK v1 registry, with the intended ownership/use definitions above. This does not approve any future storage, AEAD, audit, or recovery implementation.

Compatibility rules proposed for review:

- The exact bytes of an existing ARK/v1 label are immutable. Renaming or changing a label changes derived output and is a cryptographic compatibility break.
- Existing variants must not be silently repurposed for a different semantic domain.
- A genuinely new purpose may be added additively only after its owner, threat model, lifecycle, and compatibility impact are reviewed.
- A purpose that needs materially different semantics must use a new protocol version or separately reviewed label; do not redefine an existing v1 label.
- Deriving two outputs under two labels does not create or validate the parent key, authenticate metadata, allocate AEAD nonces, or authorize access.

This decision remains proposed until the Crypto owner explicitly confirms it and an independent reviewer accepts the purpose registry. No breaking label change is made in this PR.

## 4. HKDF behavior

- Hash: SHA-256.
- Construction: RFC 5869 Extract-and-Expand.
- Production output length: fixed 32 bytes (`KEY_LEN`), wrapped in `Zeroizing<[u8; 32]>`.
- IKM minimum: 16 bytes; recommended root material: 32 bytes.
- Context: exact registered `ARK/v1/<purpose>` byte label; unknown or ad-hoc labels are rejected.
- Optional HKDF Extract salt follows RFC 5869 semantics and is distinct from the mandatory password salt used by Argon2id.
- Raw password bytes must never be passed directly as HKDF IKM.
- Derived outputs must not be logged, formatted, or reused across unrelated purposes.

The six purpose outputs are covered by tests that exercise each registered enum value and verify distinct derivation outputs for distinct labels using a non-secret fixture. These are regression tests for label wiring, not proof of source entropy.

## 5. Secret-safe diagnostics

The public HKDF error enum is fieldless and emits static text. `HkdfIkm` Debug output redacts bytes and exposes only length. Derived outputs are held in zeroizing buffers. The test failure messages avoid printing IKM, salt, PRK, OKM, or derived-key bytes.

## 6. Deferred boundaries

- Root-key generation and IKM provenance enforcement belong to the future credential/key-lifecycle owner; the current workspace has no such service.
- Public authentication/service error mapping is deferred to [Issue #32](https://github.com/RhinoGuard/ARK/issues/32).
- Authenticated persistence and metadata migration are deferred to [Issue #33](https://github.com/RhinoGuard/ARK/issues/33).
- Independent security review remains required by ARK-SEC-032.
